WaGuard

A self-hosted, headless WhatsApp API that links your own number by QR — like WhatsApp Web — with no Meta Cloud API, no Business account, and no third-party provider. Its single overriding goal: drive the ban risk as close to zero as possible through human-like behavior, backed by a health-feedback monitor that learns from every warning sign.

Node.js TypeScript Baileys Fastify SQLite Docker OpenAPI / Swagger

Reality note on bans: This uses the unofficial WhatsApp Web protocol, which is against WhatsApp's Terms of Service. There's no cap or waitlist, but there is inherent ban risk. WaGuard minimizes it as far as technically possible — it can't eliminate it, and WhatsApp never discloses the exact reason for a ban. The health monitor captures the best available signals instead.

What the app does

  • Link by QR

    Link one or more existing numbers by scanning a QR code, with automatic reconnect that keeps sessions alive.

  • Send via API

    A token-secured API any app can call to send text, image, document, audio, and video messages.

  • Anti-ban pacing

    Every send flows through a queue that mimics a human — randomized delays, per-number limits, warm-up, quiet hours.

  • Receive via webhooks

    Captures incoming messages and delivery/read status and pushes them to your systems via signed webhooks.

  • Health & feedback monitor

    Watches each number for danger signs, warns early, and logs a diagnostic timeline around any flagging event.

  • Consent guardrails

    Blocked or non-consented recipients are never messaged — cutting the single biggest ban trigger.

  • Admin dashboard

    A minimal dashboard to link numbers, manage tokens and webhooks, and inspect health, queue, and logs.

  • Self-serve API docs

    A live, always-accurate docs page with a downloadable OpenAPI spec any downstream system can build against.

Already provided by the existing codebase

This is a fresh, empty project — there is no starter template. Everything is built from scratch across the milestones below. The stack is deliberately lean (Node.js + TypeScript, Baileys, Fastify, SQLite) so the service stays fast, responsive, and lightweight, and can run as a single small service on a cheap VPS. The recommended way to run it is a single Docker container — for ease, one command (e.g. docker compose up) brings up the whole service with only Docker on the host, and all persistent data lives on a mounted volume. A direct, non-Docker run (Node.js on the host) is also supported as a fallback — Docker is preferred for convenience, not required.

Out of scope (v1)

  • Group messaging — different rules and ban dynamics; deferred to v2.
  • Bulk / broadcast campaigns — highest ban-risk feature; needs its own careful design in v2.
  • Template / message library — saved reusable messages; v2.
  • Contact import — CSV/address-book import; v2.
  • Auto-reply / chatbot / AI responses — WaGuard sends and receives; the downstream app decides replies.
  • Multi-user / team accounts & roles — single admin owner in v1.
  • Billing / subscriptions / metering — your own self-hosted service; no payment layer.
  • Analytics & reporting dashboards — health monitoring stays, but no campaign charts.
  • Mobile app / browser extension — API plus a minimal web dashboard only.
  • Cloud multi-tenant SaaS — v1 is single-tenant, self-hosted for your own numbers.
  • ML / adaptive auto-tuning of anti-ban params — v1 is rule-based and logs evidence for you to learn from.
  • Proxy / IP rotation — not in v1.

Milestones

1

Foundation & Access

Stands up the running service, storage, admin login, API-token authentication, and the live (initially empty) auto-generated API documentation page.

What gets built

  • Single Docker container (recommended), one command to start — only Docker on the host; data on a mounted volume; non-Docker run supported as fallback
  • Password-protected admin login (single owner)
  • Create, name, and revoke API tokens
  • Token auth: calls without a valid token are rejected
  • Live auto-generated API docs page + downloadable OpenAPI spec
  • Dashboard shell with navigation for later pages

Not in this milestone

  • Any WhatsApp connection or QR linking
  • Sending or receiving messages
  • Anti-ban engine, queue, health monitor, consent
  • Multiple admin users or roles

Done when: You can bring the whole service up with one Docker command on a host that has only Docker installed (non-Docker run also works as a fallback), log in, create and revoke a token, get rejected calling the API without one, open the live docs page and download the OpenAPI spec, and confirm data survives a container restart.

2

Link a Number

Adds the WhatsApp connection: scan a QR code to link a number, keep it connected, and see its live status.

What gets built

  • Dashboard QR code to scan from WhatsApp → Linked Devices
  • Multiple numbers, each with a live status badge
  • Automatic reconnect without re-scanning
  • Re-scan prompt only when the session is truly invalidated
  • Unlink / log-out per number; status API endpoint

Not in this milestone

  • Sending or receiving messages
  • Pairing via phone-number code (v2)
  • Automatic failover to a backup number

Done when: You can scan the QR, see the number go "linked", restart the service and have it reconnect without re-scanning, and unlink from the dashboard.

3

Safe Sending

Delivers the core value: a send API whose messages flow through the anti-ban queue and pacing engine so they go out like a real person sent them.

What gets built

  • Send API for text, image, document, audio, video (URL or upload)
  • Trackable status: queued → sent → delivered → read / failed
  • Anti-ban engine: delays, typing sim, per-number limits, warm-up, throttling, quiet hours
  • Scheduled sends and queue visibility with auto-retry
  • Pause/resume a number's queue; queue survives restart

Not in this milestone

  • Receiving messages or webhooks (M4)
  • Health monitor and consent guardrails (M5)
  • Multi-recipient, groups, broadcasts (v2)
  • Buttons/lists, polls, reactions, edit/delete sent

Done when: You can call the send API for text and media, watch it pass through the queue with a human-like delay and typing indicator, see status reach delivered/read, schedule a future send, and pause/resume a number.

4

Receiving & Webhooks

Closes the loop: incoming messages and status updates are captured, stored, and pushed to your downstream systems.

What gets built

  • Incoming messages captured and stored
  • Webhook config page: URL, event types, recent deliveries
  • Events for incoming messages + outbound status updates
  • Incoming media stored with a reference; signed payloads
  • Automatic retry if the endpoint is temporarily down

Not in this milestone

  • Health monitor and consent enforcement (M5)
  • Multiple webhook endpoints / per-event routing
  • A pull/polling API for message history

Done when: You can configure a webhook URL, message your linked number from another phone, and see a signed webhook fire with the message and media reference, plus status-update webhooks for outbound messages.

5

Health & Consent

Completes the anti-ban story: continuous health monitoring with a diagnostic feedback log, consent guardrails, and final docs polish.

What gets built

  • Live health status per number (healthy / at-risk / flagged)
  • Danger-sign detection + early warnings to dashboard & webhook
  • Health Event log with activity snapshot + post-flag timeline
  • Auto cool-down of at-risk numbers
  • Consent guardrails: block rejects, unknown-policy, STOP auto-block
  • Searchable contacts, invalid-number rejection, docs "try it" + full spec

Not in this milestone

  • Predictive ML risk scoring / parameter auto-tuning
  • Automatic remediation beyond cool-down
  • Opt-in web forms, double opt-in, consent import (v2)
  • Per-number (rather than global) consent policies

Done when: You can see live health per number, trigger and view a health event with its snapshot, watch an at-risk number auto-cool-down, have a send to a blocked contact rejected, auto-block via inbound STOP, and use "try it" on the finished docs.
